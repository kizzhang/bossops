# BOSS 直聘招聘端作业规范

这份规范来自一次真实招聘中四天的操作：同一个账号在网页端和桌面客户端**各触发过一次「安全验证」**，网页端随后被限制使用。
下面每条规则都对应一次真实出过的事，原委见 `references/incidents.md`。

## 一、这份规范管什么、不管什么

它管的是：**怎样在用户自己的招聘账号上低风险地干活，以及风控一旦出现怎样正确收手。**

它不提供、也不要去研究让自动化躲过平台识别的手段：模拟鼠标轨迹、伪造打字节奏、隐藏输入的注入标记、改设备指纹/UA/代理、解验证码、开小号分流。
原因很实际：程序发出的点击和按键在系统层面带有「注入」标记，客户端能看到，再怎么随机也改变不了这一点。
往「更像人」上加码只是把封号往后推，押上的是用户的**实名招聘账号**。

所以下面的「随机、放慢」是**限流**——控制单位时间的操作量和外发量，别像群发——不是伪装。

## 二、开工前先回答三个问题

**1. 走哪个通道？**
- **桌面客户端**：需要会话里有 computer use 工具（通常要新开会话才加载）。做法读 `references/app-desktop.md`。
- **网页端（Chrome 扩展）**：做法读 `references/web-chrome.md`。网页端被限制过的账号，只有用户明确说已恢复、并同意使用时才用。
- 两条都不通：把文案整理成可粘贴版交给用户自己发，不要硬试。

**2. 账号今天的风险状态？**
看交接文件和最近的日志：今天有没有弹过安全验证、掉过线？今天已经发了多少条？
**今天弹过验证 → 今天不再由 AI 在 BOSS 里点击或输入**（见第三节 M1）。

**3. 这一批用哪种作业模式？** 见下一节。

## 三、两种作业模式

| | M1 只读 | M2 先看后报、同意再动 |
|---|---|---|
| AI 在 BOSS 里 | 只截屏读内容，**不点击、不输入** | 按批次点击、输入、发送 |
| 用户 | 自己打开会话、粘贴、发送、填表 | 每批开始前审批「看谁、发什么」 |
| AI 在 BOSS 外 | 读简历/回复、筛选、拟文案、排期、换算时区、记台账、做发送队列 | 同左 |
| 什么时候用 | **当天弹过安全验证**、掉线未恢复、用户要求 | 默认 |

M2 的流程：
1. 先只读，把这一批「要看谁、要做什么、每条文案原文」报给用户。
2. 用户明确同意这一批后才动手。没有这一批的同意，不在 BOSS 里点击或输入。
3. 用户说了「直接发」的，视为这一批的同意，但只管这一批。

M1 下给用户的「发送队列」格式：每条一行——发给谁、在哪条会话（姓名 + 学校 + 当前公司，便于搜到）、整段可复制的文案、发完打勾。

## 四、节奏与外发量（限流）

所有延时都要随机，区间之间互相独立，不要写死固定值：

| 场景 | 区间 |
|---|---|
| 点开一个会话前 | 0.8–2.5 s |
| 读完资料、进入下一个前 | 2–5 s |
| 每处理 3–5 人（个数也随机）后的长停顿 | 10–25 s |
| 两条消息发送之间 | 15–40 s |
| 一条消息内部各步骤（聚焦→输入→核对→发送） | 每步独立随机，**区间要宽**（比如 0.8–4 s），不要用 1.3–1.6 s 这种窄区间——那等于定频 |
| 滚动一屏 | 随机步长 300–900 px + 随机间隔 0.6–1.8 s |

**不准私自调快。** 觉得按这个节奏跑不完，先问用户，不要自己改参数。

**外发量比单条节奏更重要。** 第二次验证发生在 40 分钟内开了 14 个会话、发了 9 条长消息之后。

| 上限（默认值，用户可按自己账号调） | |
|---|---|
| 每小时外发长消息 | ≤ 6 条 |
| 每天外发 | ≤ 20 条 |

- 把一天的外发拆到不同时段，不要一小时内集中发十几条。
- 读的量也算：同一天读几百份简历本身就是异常量。大批只读核查尽量分到不同时段。

**内容去同质化。** 反垃圾模型会看内容相似度，和用什么工具发无关。每条消息的开头和中段按候选人本人的经历写，不要大段复用同一句话。

## 五、发前核验与防误发

一条消息发错了人或发重了，比慢更糟。

- **打开会话后先核对身份**：面板姓名 + 学校/年龄/当前公司/期望薪资，至少两项和目标一致才输入。不一致就停，不要「差不多就发」。
- **同名要消歧**：搜出两个同名或同姓「X先生」的，按学校、年龄、公司逐项对，找到唯一匹配的那个。
- **先查我方是否已经回过**：用户自己也可能在同时操作 BOSS。打开会话先看最近几条消息——我方已经回复、已经发过邀约的，**跳过并报给用户**，不要再发一条。
- **单段、无换行**：BOSS 聊天框回车即发送，带换行会被拆成好几条轰炸候选人。
- **输入后、发送前再核对一次输入框里的完整文字**（截图或读 DOM），确认是这一条、是给这个人的，再点发送。
- **文案先给用户过目**，除非用户明确说了「直接发」。

## 六、正式面试邀约（「约面试」按钮）

表单字段：面试类型（线上）→ 招聘职位 → 面试平台选「其他方式（腾讯会议、钉钉、飞书）」→ 具体平台 → 会议信息填会议号 → 备注（≤140 字）→ 日期 → 开始时间 → 联系人（自动带出）。
- 表单**没有时长字段**，「预计 45 分钟」这类信息写进备注。
- **发送前核对整张表单**，尤其日期——日历控件里过去的日期是灰的，可以顺便确认当前北京日期。
- **改期/撤销**：在候选人会话里点「查看面试」取消旧邀约，再用「约面试」重发。不清楚旧卡用的哪个平台，先看一眼卡片再照填。
- 付费推广弹窗（曝光刷新卡等）一律关掉，不买。

## 七、数据落地与回执

- **每批结果立刻写到磁盘**，不要只放在页面变量或内存里。页面一跳转/一崩就全丢——实测丢过 40 条。
- **每条发送截图回执**，存到 `receipts/<批次名>/NN_<候选人>.png`，并在发送日志里登记时间（北京时间）、状态（送达/已读）、核对了哪些字段。
- 约定的面试同步到一个 `.ics` 日历文件（取消的标为已取消，不要删）。
- 一轮结束更新交接文件，写清已发/待发/跳过及原因，防止下一个会话重发。
- 关键文字（人名、学校、日期）**用读 DOM 或局部放大复核**，不要凭一眼截图——实测把形近字认错过，并写进了两份文件。

## 八、出事时怎么收手

| 现象 | 立即做 | 不要做 |
|---|---|---|
| 出现「安全验证」页面 | **立刻停手**，告诉用户由本人完成验证；当天转 M1 | 自己点验证、换个办法继续 |
| 被弹回登录页/二维码页 | 最多再试 3 次导航，仍失败就停，请用户重新登录 | 反复刷、代用户登录 |
| 页面卡死、脚本调用超时 | 停止当前批次，确认是否误发（看最后一步是否已到「发送」），重载一次 | 连续重载、马上接着跑 |
| 发现可能发错/发重 | 停，截图，报给用户，让用户决定是否撤回或补一句 | 自己再发一条「更正」 |

验证完成后，当天让账号冷却，不要再由 AI 在 BOSS 里操作。

## 九、时间与屏幕

- BOSS 显示北京时间（UTC+8）。用户不在东八区时，任何排期都**换算并向用户复述两边时间**，注意对方地区的夏令时切换。
- 本地沙箱的时区库可能不可靠。换算以一个实测锚点为准：BOSS 界面上的北京时间 + 浏览器/系统报告的本地时间。
- **桌面客户端作业会占用用户的屏幕和鼠标。** 用户有面试或会议时，至少提前 15 分钟停手并告知「屏幕交还给你」。

## 十、不做清单

- 不解、不点安全验证 / 滑块 / 验证码
- 不模拟鼠标轨迹、不伪造按键节奏、不隐藏注入标记、不改设备指纹/UA/代理
- 不为了「像人」把粘贴改成逐字敲
- 不开小号、不多账号分流
- 被风控标记后不「换个法子继续」
- 不代用户登录、不碰账号凭据
- 不购买任何付费推广
