# 网页端（Chrome 扩展）操作细则

> 网页端被限制过的账号，只有用户明确说已恢复、并同意使用时才用这份。
> 先读 SKILL.md 的第三、四、五节。

## 页面结构（BOSS 招聘端「沟通」页，2026-10 实测）

- 列表项：`.geek-item-wrap`
- 右侧会话面板：`.chat-conversation`（面板第一行是姓名；含「沟通职位：」一行）
- 列表滚动容器：`.user-list`，**虚拟滚动**，DOM 里始终只有约 40 个节点
- 列表底部有「滚动加载更多」/「没有更多了」
- 职位发布表单在同源 iframe 里，`read_page` 读不进去，要用 JS 访问 `iframe.contentDocument`

## 定位与读取

- 推进虚拟列表：对当前最后一个 `.geek-item-wrap` 调 `scrollIntoView({block:'end'})`。直接设 `scrollTop` 会被打断——点击某一项后列表会自己滚回选中项。
- 到底部后**停住自然等懒加载**，不要催。
- 去重用**姓名**：列表项文本会变（未读角标消失），用它做键会重复抓。姓名取列表项文本去掉开头的数字和时间后的第一个词。
- 关键文字用 JS 读 DOM 文本确认，不要凭截图认字。

## 批次与超时

- CDP `Runtime.evaluate` 有 **45 秒硬超时**。按 SKILL.md 的节奏，一批 7–9 人正好，再多就会超时整批白跑。
- **每批的数据都 `return` 回来落盘**，不要只累积在 `window` 变量里——页面一跳转全丢。
- 超时后数据可能还在页面里，先取回再继续。

## 防误发的写法

把「定位 + 核对」和「输入 + 发送」放进同一个 `browser_batch`，但定位那步要**核对失败就抛错**，让整批中止：

```js
// 示意：找不到人、或面板姓名对不上，就 throw，后续的输入和发送都不会执行
const r = await seek(name);
if (!r.ok || r.name !== name) throw new Error('ABORT: 未能确认打开 ' + name);
```

输入后、点发送前，用 JS 读一次输入框内容确认是这一条。

## 明令禁止的写法

这些在实测中把渲染进程跑死，并疑似导致会话掉线和网页端被限制：

```js
// ✗ 定频横扫整个列表
for (let y = 0; y <= el.scrollHeight; y += 500) { el.scrollTop = y; await sleep(260); }

// ✗ 反复跳到底部催加载
for (let i = 0; i < 8; i++) { el.scrollTop = el.scrollHeight; await sleep(1500); }

// ✗ 合成滚动事件
el.dispatchEvent(new Event('scroll', { bubbles: true }));
```

需要全量复查时，用随机步长 300–900 px + 随机间隔 0.6–1.8 s，并且分段做。

## 掉线与卡死

- 被弹回首页或二维码登录页：最多再导航 3 次，仍失败就停，请用户重新登录。
- 渲染进程无响应（截图也超时）：先确认最后一步有没有到「发送」，再重载一次；不要连续重载。
- 页面内注入的辅助函数（如 `seek`）重载后会丢，需要重装。
